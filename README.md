# WorkflowIR Harness

[中文主页](README.md) · [English](README_EN.md)

![WorkflowIR-Harness：更少上下文，更稳定的工作流](assets/hero-opencode-vs-workflowir.svg)

> 面向预生成 Dify 工作流配置的确定性运行验证 Harness：负责兼容适配、真实执行、输出契约检查和有界修复；Workflow IR 当前是独立验证原型，尚未接入可复现的自然语言生成 CLI。

## 16 项公开任务、96 个逻辑 Trial：不是单个幸运样本

**16 项公开任务 × 3 组固定输入 × 2 套系统 = 96 个系统侧逻辑 Trial**，组成 **48 组同输入配对对照**。每套系统在每项任务上使用一份冻结的预生成工作流；同一份配置必须通过全部 3 组输入，才记为一个稳定工作流。增量复测会复用已通过记录，因此“96”是比较矩阵中的逻辑 Trial 数，不表示每次报告都重新执行了 96 次。

> **历史结果口径：** 下表是确定性结构校验器和“只要结果含未验证文件字段（包括文件与文本混合输出）就记为 unverified”规则引入前的 pre-P0 快照。当前代码尚未按新协议完整重跑，因而这些数字不能表述为新版本已复现结果。

![配对评测：稳定工作流与任务成功率](assets/scoped-evaluation.svg)

| 方法 | Dify 执行成功 | 运行验收 | 稳定运行工作流 | 语义 Judge 通过 | 稳定语义工作流 |
|---|---:|---:|---:|---:|---:|
| 官方 Agentic 产物 | 35/48（72.9%） | 32/48（66.7%） | 10/16 | 23/48（47.9%） | 5/16 |
| **WorkflowIR-Harness** | **45/48（93.8%）** | **45/48（93.8%）** | **15/16** | **34/48（70.8%）** | **9/16** |

其中，Dify 执行成功率由 **72.9% 提升至 93.8%**；进一步要求必需输出存在且非空的运行验收率由 **66.7% 提升至 93.8%**。两者不可混为同一个指标。

全部 19 个 Harness 工作流中，18/19 连续通过 3 组运行输入；Harness 侧共 57 次系统运行，其中 54 次通过（94.7%）。剩余 3 次保留为 **StudyPlanner_3** 超时，没有从结果中删除。

| 方法 | 生成 Token | 模型调用 | Dify 执行 | 语义成功 |
|---|---:|---:|---:|---:|
| OpenCode Agentic | 35,457 | 2 | 3/3 | 0/3 |
| **WorkflowIR-Harness** | **24,877** | 5 | 3/3 | **3/3** |

在这份选定日志中，Harness 使用了更多模型调用但记录到更少的生成 Token；其产物还通过显式输出契约分离了知识总结与 Mermaid 源码。该单案例不能单独证明 Token 差异由某个组件造成。

> Token 数据仅来自 `Mermaid_2` 这一选定案例，不是 16 项任务的均值或总体结论，也不是官方排行榜成绩；当前仓库的运行 CLI 不复现上游生成过程。生成 Token 不包含 Dify 执行工作流时的业务模型消耗。完整记录见[案例复盘](docs/CASE_STUDY_MERMAID2.md)。

## 它解决什么问题

直接让大模型一次性生成完整 Dify DSL，既要理解需求，又要记住大量 Node Schema、变量引用和边连接规则。配置一旦变长，常见失败包括：

- 边没有指向有效节点，或 Router 分支缺少出口；
- 节点存在，但输入变量引用了不存在的上游输出；
- 拓扑合法，却无法被 Dify 导入或实际执行；
- 每次失败都重新生成整份大 JSON，Token 多且修复方向不明确。

当前仓库可复现的主链路从**已经生成的 YAML 工作流产物**开始：

```text
Pre-generated Dify YAML
        ↓
Requirement/Runtime Contract Patch
        ↓
Compatibility Adapter → Import/Publish → Real Execution
        ↓
Output Contract Check → Trace-based Bounded Repair → Full Rerun
```

仓库另含 Workflow IR、拓扑/绑定校验和类型契约原型，用于验证“缩小生成目标空间”的设计；它目前没有与自然语言重写、检索和模型生成串成可运行的端到端 CLI。

## 核心设计

### 1. Workflow IR 与契约校验原型

原型使用较小的中间结构表达节点、边、分支和变量映射，并提供确定性的图与引用结构检查。该校验器能够发现缺失端点、非法边和部分引用问题，但尚不保证变量字段名正确、输出类型正确、文件内容有效或业务语义满足。它验证了将业务图结构与平台字段分离的可行性，但当前公开代码尚未提供自然语言到该 IR 的正式生成器及 IR 到完整 Dify DSL 的通用 CLI。

### 2. 预生成产物的确定性适配

Runner 读取冻结的 YAML，为基线和 Harness 产物应用共享的环境兼容修复，并仅在 Harness 侧应用需求契约修复。模型、插件、文件描述符和部分平台字段由 Adapter 按当前 Dify 环境补齐，同时记录每项修改。

### 3. 真实执行与分层失败记录

系统将配置导入并发布到 Dify，使用固定输入真实运行，分别记录 Dify 执行、必需输出契约和语义 Judge 结果。真实 Runner 记录导入、输出契约、节点执行和基础设施失败；Graph 与 Binding 的细粒度分类主要来自独立 IR/Validator 原型，不能表述为主评测链已经统一覆盖四层。

### 4. 有界 Trace 修复

| 错误层 | 典型问题 | 处理方式 |
|---|---|---|
| Graph | 空边、孤立节点、非法连接、Router 分支不完整 | 在 IR 原型中拒绝无效结构 |
| Binding | 变量不存在、上下游类型不一致、必填输入缺失 | 契约检查或确定性重绑 |
| Execution | 配置合法但 Dify 运行报错 | 根据 Trace 向可修复节点注入有限次数提示 |

每次运行时修复后重新执行完整工作流；连续失败或节点规模超过能力边界时停止自动重试，避免无上限消耗。

### 5. 实验性修复记忆（不计入主结果）

仓库包含按任务隔离的修复策略存储，以及 Candidate、Active、Quarantined 生命周期原型。当前保存的是经执行与输出契约复验后的通用文字修复策略，不是成功代码 Diff、完整 Trace 或可执行 Skill；现有三输入协议也没有提供独立 held-out 输入证明 Warm 增益。

公开的 93.8% 运行验收结果关闭了经验池，不能归因于该原型。它目前只支持单进程 Runner 内的多线程访问，不声称多进程安全或在线自进化收益。

## 如何判定“成功”

一个 Trial 只有同时满足以下条件才记为通过：

1. **结构有效**：节点、边、Router 与 Merge 满足图约束；
2. **引用有效**：节点输入能够解析到合法的上游变量；
3. **平台有效**：Adapter 生成的 DSL 能被 Dify 导入；
4. **真实执行成功**：Dify 运行状态成功，没有未处理的节点异常；
5. **语义代理状态**：只有完全不含未验证文件字段的输出才进入官方 Resolve Prompt 和同模型、温度 0 Judge；新 P0 规则将任何含文件字段的结果（包括文件与文本混合输出）标记为 unverified，等待独立内容检查。

因此，“LLM 返回了一份 JSON”不等于成功，“Dify 接受了 DSL”也不等于运行验收通过。语义结果仍是低成本代理：没有独立人工复核，输出最多保留 16,000 字符；历史快照曾自动接受未检查文件内容的结果，新协议已将所有含未验证文件字段的结果改为 unverified。

## 评测设计

### 评测对象

- **Agentic 基线**：把 benchmark 任务交给通用 Coding Agent 生成并修复工作流；
- **WorkflowIR Harness**：对冻结的预生成工作流应用共享兼容适配、Harness 侧需求契约修复、Dify 执行、输出检查和有界定向修复。

两组冻结产物都经过相同的运行环境兼容处理；Harness 侧额外的需求契约修改属于完整 staged artifact bundle 的一部分。当前没有组件消融，因此总体差异不能归因于 Workflow IR、Adapter 或某一种修复策略。

### 任务规模

当前配对实验覆盖 **16 项公开工作流任务**，包括线性生成、条件路由、多分支汇聚、结构化转换、文档/代码输入处理、模板输出、变量聚合和失败兜底等结构。每项任务使用 3 组固定输入，两套系统形成 48 组配对输入、96 个系统侧逻辑 Trial。

### 主要指标

| 指标 | 回答的问题 |
|---|---|
| 可导入率 | 配置能否被真实 Dify 接受？ |
| Dify 执行成功率 | 工作流是否在 Dify 中运行结束且无节点异常？ |
| 运行验收率 | Dify 执行成功后，必需输出是否存在且非空？ |
| 有界修复记录 | 运行时失败是否保留 Trace、修复动作与完整工作流重跑结果？ |
| 语义 Judge 通过率 | 低成本 Judge 是否接受非文件业务输出？ |
| 生成 Token（仅 Mermaid_2） | 选定案例中，上游生成阶段消耗多少模型上下文？ |

### 为什么不做 JSON 逐字段匹配

同一个任务可能存在多套等价拓扑，节点 ID、画布坐标和部分平台默认字段也不会影响执行结果。因此主评测使用 Dify 执行、必需输出契约和语义代理结果；IR 原型另行检查拓扑与变量引用，而不是要求产物与某一份参考 JSON 完全相同。

## 责任声明

本项目使用公开 benchmark 的任务和预生成产物进行事后工程复测，但采用的是自定义运行验收协议，**没有完整遵循官方 benchmark 协议，因此不宣称官方排行榜成绩**。当前结果主要比较两组冻结产物在相同 Dify 环境中的执行、输出契约与语义代理结果；不构成自然语言生成端到端消融。

依赖 GitHub、TTS 或其他不可控外部服务的任务不混入本地 Dify 主结果；这类任务应在依赖可用时单独报告，避免把外部服务故障记成工作流生成失败。

## 项目定位

WorkflowIR Harness 不是 Dify 的替代品，也不重复实现 Dify 的运行时、调度和插件生态。它关注的是 Dify 之前最容易失控的一层：

> **如何让预生成工作流在目标 Dify 环境中可导入、可执行、可检查，并为未来的 IR 生成前端提供确定性反馈。**

Dify 负责运行工作流；当前 Harness 负责适配冻结配置、执行验证和有限修复。自然语言重写、检索、IR 生成与通用 IR→Dify Adapter 仍属于待接通的生成前端。
